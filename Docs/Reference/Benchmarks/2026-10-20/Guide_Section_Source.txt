Measured 20 October 2026

TA Health Check Performance Benchmark
All six TA Health Check builds completed successfully on 20 October 2026, using demonstration datasets from 50,000 to 300,000 managed endpoints. On the measured workstation, building the Client Performance, PerfMon and FillDB reports took 2 minutes 16 seconds to 12 minutes 7 seconds. Peak report process memory increased from 1.68 GiB to 6.66 GiB. These results help plan build time and available memory; they do not establish a minimum supported computer specification.

Workstation used
Lenovo 21DDS1XW00 laptop; Intel Core i9-12900H with 14 physical cores and 20 logical processors; 64 GiB installed RAM (63.7 GiB visible to Windows); WD PC SN810 2 TB NVMe SSD. Windows 11 Enterprise build 26200, 64 bit; Python 3.13.14. Input, temporary and output files were on the local C: SSD. The laptop was connected to AC power using the Balanced power plan.

Practical memory planning
For a workload comparable to the 300,000-endpoint fixture, plan for about 10 GiB of available RAM after selecting and scanning the dataset and opening other required applications. This allowance rounds up 1.5 times the observed 6.66 GiB peak. It is planning headroom, not a tested minimum, an enforced limit or a guarantee. The benchmark computer had 64 GiB installed; lower-memory computers and the complete desktop application were not benchmarked.

What was measured
Each size ran once, sequentially, through the production report engine using a fixed source snapshot. Timing includes process startup, input discovery, analysis, chart rendering, and Excel and Word output. It excludes preparing the input copy, the 15-second baseline measurement, human module selection, review pauses, output verification and opening Word. The packaged executable and desktop interface were outside the measurement.

Endpoint records, client settings and UDP distributions scaled with device count. Each size used the same six-hour PerfMon capture with 360 readings and 232 counters. Activity logs, FillDB, deployment content and hardware examples were fixed. The normal input discovery selected the supplied Top 10 summary CSV; raw property-timing XML aggregation was not exercised. Longer captures, larger logs or property catalogues can require more time and memory independently of endpoint count.

Resource behavior
During the 300,000-endpoint build, available system RAM fell from a 35.97 GiB baseline to a 30.69 GiB minimum. Report processes consumed 728 CPU-seconds over 727 elapsed seconds, averaging about one logical core, or 5.0% of this 20-logical-processor machine. Client Performance accounted for 711.3 seconds; PerfMon took 11.9 seconds and FillDB 2.5 seconds. Client Performance therefore drove about 98% of the build time. These figures do not establish a minimum CPU count or a GPU requirement.

Memory in the table is the Windows job peak committed memory for the engine and all descendant processes, including chart renderers. This is an allocation measure, not physical RAM alone. Available system RAM and CPU, disk and paging activity were sampled every second; these system measurements include other applications. Shared pages can be counted more than once in summed working sets, so those sums are not used as the primary memory measurement.

How to use these results
These are observations from one workstation and one pass per size. Background applications remained open and their load varied. Input copying occurred before timing and may have warmed filesystem caches. Results do not measure cold reads, network-share performance or repeat-run variability. Use the table as a planning reference, then check available memory and elapsed time with the actual customer dataset.

Every run produced three Word Mini Reports, two Excel workbooks and 23 PNG charts. Output structure and expected files were checked, including the Client Performance source-row count. Approximately 2% of endpoints were deliberately marked as not reporting; at 300,000 endpoints, the workbook contained 293,975 reporting rows and 6,025 non-reporting endpoints.

Reuse in the Master Class guide
These measurements were taken with TA Health Check. They may be reused in the Master Class user guide for its equivalent Client Performance, PerfMon and FillDB implementation, with the measurement date and scope retained. Master Class was not separately benchmarked. Reassess applicability if its processing, dependencies, packaging or selected workload changes.
